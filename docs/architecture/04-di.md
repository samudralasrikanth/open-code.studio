# Dependency Injection Architecture

> Version: 1.0

---

# Purpose

Dependency Injection (DI) manages object creation and dependency resolution throughout Open Code Studio.

The DI container ensures that components depend on abstractions instead of concrete implementations.

Goals:

- Loose coupling
- Testability
- Replaceable implementations
- Lifecycle management
- Simplified construction

---

# Why Dependency Injection?

Without DI:

```text
EditorService
    ├── new Logger()
    ├── new WorkspaceService()
    └── new ConfigService()
```

Problems:

- Tight coupling
- Difficult testing
- Hardcoded implementations
- Complex constructors

With DI:

```text
EditorService
        │
        ▼
DI Container
        │
        ├── ILogger
        ├── IConfigurationService
        └── IWorkspaceService
```

---

# Architecture

```text
Application Startup
        │
        ▼
Register Services
        │
        ▼
Build Container
        │
        ▼
Resolve Dependencies
        │
        ▼
Application Ready
```

---

# Service Registration

Every platform service is registered once.

Example:

```ts
container.registerSingleton(ILogger, LoggerService);

container.registerSingleton(IConfigurationService, ConfigurationService);
```

---

# Service Lifetimes

| Lifetime  | Description                           |
| --------- | ------------------------------------- |
| Singleton | One instance for application lifetime |
| Scoped    | One instance per scope/workspace      |
| Transient | New instance every resolution         |

Recommended defaults:

- Logger → Singleton
- Configuration → Singleton
- Workspace → Scoped
- Command Context → Transient

---

# Constructor Injection

Preferred pattern:

```ts
class EditorService {
  constructor(
    private readonly logger: ILogger,
    private readonly workspace: IWorkspaceService
  ) {}
}
```

Avoid service locators and global singletons.

---

# Interface Rules

Every service must expose an interface.

```ts
interface ILogger {}
interface IStorageService {}
interface IAIProvider {}
```

Consumers should never depend on implementation classes.

---

# Testing

Tests replace implementations with mocks.

```text
ILogger
    ↓
MockLogger

IWorkspaceService
    ↓
MockWorkspace
```

This allows deterministic unit tests without touching production infrastructure.

---

# Anti-Patterns

Avoid:

- `new` inside business logic
- Global mutable singletons
- Service locator usage
- Circular service dependencies

---

# Dependency Graph

```text
UI
 ↓
Application
 ↓
Platform
 ↓
Infrastructure
```

Dependencies must always flow downward.

---

# Summary

Dependency Injection provides a stable, testable foundation by separating object creation from business logic and enforcing interface-based design.
